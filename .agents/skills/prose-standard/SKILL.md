# dsh-recall-plugin 散文与文档标准

写够保住契约，再删推理转录、重复和装饰。契约是调用方、被调用方、实现方、生产者或消费者所依赖的义务、不变量、前置条件、后置条件或兼容性承诺。本 skill 拥有编辑判断权、必需覆盖要求，以及文档结构与行文规范；文档的归类、命名与生命周期以 [docs/README.md](../../../docs/README.md) 为准；猎杀并修复推理转录泄漏用 [trim-cot-leakage](../trim-cot-leakage/SKILL.md)。这是指导，不是脚本。

把「契约」「边界」「形态」「面」「缝」「门禁」「词汇」当作使用前先核对的词，而不是禁词。先问：更准确的规则、API、字段集、类型、校验、时序点、组件划分或失败状态能否更好地陈述事实？当它确实指称那个技术对象时（包括调用方/被调用方契约与安全、进程边界），保留。

注释只写代码表达不出的非显而易见契约或理由，不复述代码已经蕴含的内容。

## 输入与排除

必须给出明确 `scope`。缺了就报告所需输入并停止，不要推断成整仓库范围，也不要开始访谈。

接受 `mode: automatic | interactive`，默认 `automatic`。只有用户明确要求提问或校准时才进入 interactive。

`mode` 决定问不问，不决定改不改：审查与审计任务只报告发现、不编辑；明确要求写入、修复或精简的任务才应用确定无疑的改动。

永久排除以下路径，即使 scope 写着整仓库：

- `docs/reference/` —— 官方文档本地镜像，第三方内容，只读不改；
- `lib/` —— esbuild 构建产物，改 `src/` 后由 `npm run build` 重新生成，不直接编辑；
- `node_modules/`；
- `docs/plans/completed/` 与 `docs/upgrade-assessments/` —— 冻结的历史记录（实施记录、验收依据、版本快照）。只有为了理解某条历史引用时才查看精确目标，禁止现代化其措辞或外链。

排除项放在包含规则之后，避免被后续 include 重新纳入。

把 `lib/`、`docs/screenshots/` 与构建派生物当作派生物处理：先改拥有者（源码、构建脚本、场景），再重新生成。README 双语对（`README.md` / `README.en.md`）没有永久的主作者方，更新哪一侧都可以，但要同步另一侧并保持结构对齐。

## 保留完整命题

编辑前先识别段落里的每个命题，逐项保留：

- 行为者与动作；
- 条件、时序与顺序；
- 模态（必须、可以、绝不）；
- 负向保证与例外；
- 所有权、副作用、失败模式与后果。

只有每个事实从句都存活、且结果更清晰时，才删形容词、重复与叙述。「字数变少本身不是改进」。

在使用点保留完整的局部契约：调用方或维护者在那里需要的行为、失败、所有权与后果。架构、理由、算法、历史与扩展示例一律积极链接到拥有者文档。一个解释只有一个家；关键契约事实可以在本地重复。

非显而易见的理由，如果省略它可能导致误用或错误的简化，就保留；否则陈述后果并把理由链接回它的归宿。

## 按位置的必需覆盖

这不是单向缩短的过程。代码、类型与结构没有传达下列必需契约时，要补写或恢复；这些事实在本地已经显而易见时，不要加注释。

- **公共 JSDoc**：写调用方可见的返回值区别、抛错或拒绝、副作用、所有权、时序、取消与持久性。
- **内部注释**：为非局部的结构、以及显然复杂的局部结构定向，包括不变量、竞态顺序、所有权、安全边界与意外失败行为。删除控制流叙述和代码复述。
- **模块注释**：说明模块角色、依赖、职责与非显而易见的架构选择；架构选择链接到拥有其解释的位置。
- **测试**：只解释非显而易见的测试设计——为什么需要这个 fixture、断言、平台适配、真实入口路径或间接观察。删除走查与清单式叙述。
- **文档（docs/）**：按 [docs/README.md](../../../docs/README.md) 的归类与生命周期写；保留前置条件、必需操作、真实入口、可观察验证与必要的警告。
- **README**：写消费者契约——安装路径（`dsh plugin --profile <name> add dsh-recall-plugin` 或 link 模式）、配置字段语义与默认值、失败与限制、与 dsh 版本的兼容范围、已知坑。保留持久的缺口与维护者陷阱，不写普通清理清单。
- **计划与实施记录（docs/plans/）**：保留独有的理由、机制、备选方案、后果、已交付的验证证据与有名有姓的覆盖缺口。已完成的记录用现在时陈述已交付事实；删规划清单，不删钉住决策的证据。
- **契约与台账文档（dsh-contract.md、compat-audit.md、routing-interplay.md）**：保留依赖面事实、行为不变量、探针归属与失效症状；升级核查后更新对应行，不写推导过程。
- **技能与 agent 指令**：写行为护栏与明确的范围限制（如「指导，不是脚本/清单」）。保持工作流简洁并链接其事实源。
- **示例与配置注释**：解释访问限制、非显而易见的接线与加载顺序、安全立场、回退行为、例外与常见误用。不要叙述配置本身就展示出来的条目。
- **配置描述与用户可见文案**：措辞即行为。设置卡片、toast、错误提示的文案改动要有冒烟证据。诊断文案遵循 `src/host/diagnostics.ts` 的约定：可行动、不嵌路径、≤140 字符，且与「最近错误」共用同一套文案。client 文案属于 `src/client/`，改动后跑 `npm run build`。若授权范围内没有对应验证场景，就不要改文案，报告延后，不要把它悄悄折进纯散文编辑。
- **诊断信息**：指明失败对象或路径、违反的规则，以及非显而易见时的纠正方式。删除内部执行叙述。

保留可搜索的机制名与有意义的模态、时序、否定强调。只规范化装饰性强调。

## 文档的读者与结构

适用于 `docs/` 下的页面与 `README.md` / `README.en.md`。上一节管句子级措辞，这一节管页面组织。

- **按一个主要工作与一个读者分类页面**：用户快速开始、用户任务指南、贡献者教程、架构概览、参考、决策记录、计划与实施记录、草稿。分类从「打算怎么用」得出，不从路径得出。
- **写细节之前先定义**读者的起点状态、可观察产出、可能遇到的失败、恢复路径，以及下一步该深入到哪里。
- **页面顺序**（格式拥有者允许时）：元数据 → 标题 → 双语页的语言切换行 → 摘要（Summary）→ 目录（Table of Contents）→ 用户面向到开发者面向的内容 →（可选）进一步探索（Further Exploration）→ 需要承载活跃工作上下文时以末尾开发笔记（Dev Note）收束。小文件、生成片段与由解析器定义表头的格式可豁免，但要在格式拥有者里写明例外。
- **摘要写三到五句**：读者能做什么或观察到什么、为什么在意、主要运作模型、最重要的边界。
- **每个实质章节先给一段简短定向段落**，再上表格、代码或子标题；定向段说明该节主题与决策要点，不复述它的完整内容。
- **按读者深度排序**：基本使用（何时选择、必需输入、最短安全示例、可观察的成功、可能的恢复）→ 高级使用（配置选择、限制、操作、集成行为）→ 开发者细节（所有权、生命周期、数据模型、失败、性能、安全、值得维护的扩展点）。
- **重型开发者细节折叠在 `<details>` 里**，保持章节标题与锚点可见；折叠内容是概念级的（整体设计、主要组件架构、粗线条数据流）加源码映射与代码链接，不写完整 API 目录、逐列清单或事件载荷枚举。
- **渐进详略**：常用路径只含其产出所需事实；详尽事实保持在一个直接链接或细节层之外。为一次查找而扫过的无关材料、最大章节、标题数量与页面体积是审查指标，不是统一的字数上限。
- **小规则文件与索引**：独立可搜索的规则、实践或决策在有拥有者、变更节奏、入站链接或验证时值得自己的文件；相关文件归到描述性层级下，紧耦合的规则不要拆。索引页用三到五句解释文件夹，按用途链接直接子项，不复述子项规则。
- **移动是原子的**：文件移动、重命名或删除在同一次变更里修复所有入站链接，并同步 `docs/README.md` 的索引与相关反向引用（见其生命周期约定）。
- **双语对**：`README.md` / `README.en.md` 没有永久主作者方；更新一侧就同步另一侧，保持标题层级、列表、表格、代码块、链接与结构对齐。

## 事实验证：跑一遍，不要假设

文档陈述产品今天的行为；对操作类断言的唯一可采信证据是你运行过它。每个新文档、以及每个声称操作、命令、默认值、错误或平台差异的新段落，都必须过这道程序。

1. **写安装指引前先给主题分类。** 读事实，不读文件夹名：本仓库是 bundle 形态（`package.json` 声明 `dsh.bundle.patch`），安装走 `dsh plugin --profile <name> add dsh-recall-plugin`，npm 模式还是 link 模式由 profile 的依赖字段决定。不要写出不适用的安装指引。
2. **对当前检出运行每一个声称的操作。** 按文档将要展示的样子执行每条命令、配置片段与示例；只写观察到的内容，包括确切的输出、警告与失败方式。断言依赖你没有的密钥或网络时，明说并指出验证归属，不要替它断言行为。
3. **删掉无法复现的东西。** 绝不凭记忆、类比或相邻项目的 README 携带命令、字段、默认值或行为。主张无法复现时，修主张——不是修测试。
4. **旧文档对最新 master 检查。** 修订既有页面前先 `git fetch origin`，把该节与 `origin/master` 对比。master 上过时的陈述仍然是错的：按代码纠正，不是按旧散文纠正。
5. **改完同步另一侧。** 双语对在同一次编辑里同步，保持结构对齐。

## 行文规则

- **摘要说「能做什么」，不说「是什么」**：描述读者能用它做什么——产出、收益、何时选择、主要代价——而不是它的角色、类型或内部身份。省略源码标识符，除非读者会在配置、命令或公开 API 里直接用到它们。
- **开发者章节解释，不枚举**：折叠内容覆盖整体设计概念、架构与粗线条数据流，精确细节链接到代码；不写完整 API 目录、逐列清单、事件载荷枚举或 JSDoc 复述。
- **只写当前状态**：开发笔记之外不写兼容垫片、迁移讨论或历史（「以前」「现在」「不再」「改名」）；今天的代码与行为是唯一的主题。
- **开发笔记是唯一的草稿区**：部分想法、草稿、未定方向与工作假设只住在末尾的开发笔记（若该页面有），并明确标注非权威；其他每个章节都是打磨过的当前状态散文。工作关闭时提升持久结论、删除已解决的闲聊。
- **受控技术写作**：歧义会改变行为时，给每个句子一个明确的行为者与一个主动作；一个概念复用一个术语，不为变化而轮换同义词；偏好直接动词；一句话放一条指令，三步以上或条件用列表；拆开分号与长从句链；每段一个主题。删除无依据的质量形容词与堆叠的含糊，但保留每个事实与不确定程度。
- **绝不为长度目标牺牲契约**：`必须`、`可以`、`绝不`、时序、例外、数字与其他契约术语不得因缩短而删除或加强；拆分会隐藏条件或关系时保留长句。
- **强调纪律**：粗体保留给改变行为的从句或重要的比较，装饰性强调降为普通文本。
- **保留承重规则**：优先保留成一到三行加一个指向理由的链接；不要为了搬移可弃的推理而发明新解释。
- **行为变更先提出**：删掉一段散文如果改变的是承诺的行为而不只是解释，先提出行为变更，再改文档。

## 质量判据与审查

- **简要**：常用路径只包含其产出所需事实；详尽事实在一个直接链接或细节层之外。
- **直观**：前置先于依赖概念；一个下一步动作明显；标题使用读者会搜索的词。
- **友好**：读者能识别成功、行动前理解风险、从可能的失败中恢复、选择是否继续深入。
- **准确**：每个持久断言有一个拥有者与相称的验证路径。
- **agent 可读**：元数据、稳定标题、锚点、术语、所有权与当前/提议状态支持定向检索，无需加载全部语料。
- **新人可完成**：无仓库背景的专业工程师通过三到五个链接页面，能回答产品做什么、怎么安全使用、状态住在哪、哪个组件拥有它、怎么失败、在哪里改。

审查时对照最强拥有者：包元数据用于名字与入口点、公开类型与 JSDoc 用于 API 契约、运行时代码用于行为、测试用于已演练的失败路径、台账用于不变量与探针归属、计划与实施记录用于理由。绝不把先前的 README、讨论或报告当作比当前代码与测试更强。

只保留帮助目标读者行动、推理或避免误用的陈述；理由、历史、测试走查、重复目录与无关细节移到它们的拥有者。

## 工作流

1. 确认 scope、mode、当前分支或 PR 基线，以及适用的 `AGENTS.md` 与 `docs/README.md`。不要检查无关分支。
2. 判断一段文字前，先读拥有它的代码或文档。校准或不熟悉的案例读[校准样例](references/examples.md)。
3. 检查整个请求范围，不只检查最大的文件。用搜索和词频找候选，再逐段做语义判断。
4. 把每个候选分类为保留、补写、精简、恢复、重组或延后。只有在任务授权编辑时才应用确定无疑的改动；不要为了满足删除指标而制造编辑。
5. 先更新拥有者，再更新派生物。学到新规则后，回头复查同类段落。
6. 运行窄范围的相应检查：`npm run typecheck`、`npm test`，改过 `src/` 时 `npm run build`（产物新鲜度门禁），以及 `git diff --check`。涉及可见文案时跑对应冒烟。
7. 报告检查过的范围、确定无疑的改动、有意保留的、延后的案例，以及实际运行的检查。

## 边界情形

只有至少两个版本都满足完整命题规则、且权衡了已接受的原则、而本 skill 未能解决该权衡时，才算边界情形。只有一种保住命题的写法时，它不是边界情形。

automatic 模式下，授权时就应用确定无疑的编辑，并报告真正的边界情形，不提问。不要为了让进度好看而弱化命题。

interactive 模式下，把同类段落归到一个统辖原则下，给出两三个可行版本、推荐其中一个，并说明事实或结构上的差别。不要提供明显更差的干扰项。使用用户指定的渠道；若通过行内评论校准 PR，把推荐的暂定版本放进 diff，并把备选挂在同一行上。

用户决定后，把原则和版本提炼进[样例](references/examples.md)（不带 PR 历史或审阅叙述），并把学到的规则应用到范围内所有同类段落。
