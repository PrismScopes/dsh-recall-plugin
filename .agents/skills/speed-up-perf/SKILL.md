# dsh-recall-plugin 性能优化

把宽泛的「让它更快」转成可复现的用户路径测量，和小步、有证据、保行为的修复。这是指导，不是配额也不是脚本。

## 本项目的性能面

优化前先确认这些事实未被推翻：

- **每条用户消息一次快照**：`runShell` spawn pwsh（win32）或 bash（POSIX）跑 `add`/`write-tree`/`commit-tree`/`tag`。进程创建是主成本，win32 的 spawn 代价比 ubuntu 高一个量级——**两端分别测**，ubuntu 的数字不能外推 Windows。
- **串行队列**：preview/execute/快照/gc 同一条队列，延迟优化不能以乱序为代价。
- **启动预热**与 `ensureGit`、store 心跳（M3）在会话开始时的固定开销。
- **gc 节拍**（50 拍或 24h）与「立即 gc」的逐仓枚举，大 store 下的耗时。
- **大工作区**：`add` 全量扫盘、diff、rollback 随文件数/体积的缩放；排除表是已有的减负机制。
- **client**：快照管理的版本家族树在快照多时的渲染与搜索。

## 先测量，再排序

- 为每个候选写测量卡片：操作、负载、入口路径、时钟取法、判定指标、必须保住的行为。
- 广泛调研用户路径（发消息快照、撤回全链、打开快照管理、启动预热），变化独立的成本驱动因素（文件数、快照数、工作区体积），按实测延迟/内存 × 频率 × 置信度排序。只凭「这段代码看起来慢」下结论的，拒绝。
- 「实测」是承重词：测量结论写成 `(实测：512 层 ≈ 0.15s)` 这类带出处的边界，它在校准常量与注释里受保留规则保护（见 [trim-cot-leakage](../trim-cot-leakage/SKILL.md) 的「什么不是泄漏」）。

## 真实的合成基准

- 固定生成输入：脚本化的 fixture 工作区（文件数/体积分级），不是随手找的目录。
- 测构建产物 `lib/` 里的行为，不是 `src/`——用户跑的是产物。
- 阈值先校准再当门禁：在目标平台上量出基线分布，阈值留实测余量；拍脑袋的数字会让 CI 性能门禁变成 flake 发生器（其可靠性归 ci-test-reliability）。
- 端到端延迟与驻留内存分开测、分开判定。

## 先证明回归，再移除工作

- 改动前先在未优化的实现上跑出负载数字并留档——没有「之前的数字」的优化 PR 不可审查。
- 把失败场景最小化，对可证伪的假设排序，一次只改一个因果因素。
- 负面对照：收紧后的断言或新基准，在原实现上必须按预期失败。

## 保行为与所有权

性能证据不能取代功能证据。以下语义优先级高于速度，动了它们需要的不只是基准：

- 快照正确性：`add` 的排除语义、`write-tree` 内容、tag 主键与索引可重建性；
- 原子性：index.json/lineage.json 的 tmp+rename、损坏 fail-loud 隔离；
- 顺序：串行队列、救援回滚（H1）、intent journal 的三针时序；
- 可达性：任何缓存、并行化、跳过快照的优化，必须证明不让 blob 在 gc 下丢失（issue #18 的反面教材就在那里）。

解释不清为什么变快的优化，明确拒绝并留一行记录。

## 有界交付

- 一次优化一个有界目标，数字按「负载 → 前后数值 → 内存语义 → 行为证据 → 负面对照 → 排除项」总结，写进计划记录或注释。
- 验证按改动面跑 pre-push-checks 的矩阵；声称的性能结论必须附实际跑过的命令与平台。
