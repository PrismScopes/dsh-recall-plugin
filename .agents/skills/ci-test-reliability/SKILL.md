# dsh-recall-plugin 的可靠 CI 测试

让测试在真实 CI 拓扑下仍然正确，而不是只在安静的工作站上单独跑才通过。本 skill 拥有隔离与可靠性决策；测试分层与命令选择以 `AGENTS.md` 的「命令脚本」「测试分层」为准。这是指导，不是脚本。

## 读取拥有者规则

- 测试分层（单测 / 探针 / verify-host / 活体冒烟）与命令矩阵见 [`AGENTS.md`](../../../AGENTS.md) 的「命令脚本」「开发与验证」。
- 生命周期、子进程、取消与 teardown 的设计约束见 `AGENTS.md` 的「关键设计决策」与「已知坑」（I1-I30 台账在 [docs/compat-audit.md](../../../docs/compat-audit.md)）。
- 改动涉及 `src/host/scripts.pwsh.ts` 或 `scripts.posix.ts` 时，先读双平台契约（`src/types/scripts.ts`）与相应台账条目。
- 诊断已有的 flaky 失败走[CI flake 诊断](references/ci-flake-diagnosis.md)。

## 本项目事实

这些事实决定本 skill 在本仓库的落点，改动测试前先确认它们未被推翻：

- 开发机通常是 Windows（PowerShell 5.1 / pwsh 7 都可能），CI 跑 `ubuntu-latest`。**两端都要绿**：单跑 Windows 通过不能证明 CI 通过，反之亦然。
- CI 跑四件事：`npm run typecheck`（在单测之前，`tests/types` 编译期断言漏跑即假绿）、`npm test`（`tests/unit`）、`npm run test:client`（`tests/client`，jsdom 环境走独立 vitest 配置）、`npm run build && git diff --exit-code lib/`（产物新鲜度）。
- `npm run test:probe` 与 `npm run verify:host` 依赖本机 dsh 安装，**不进 CI**，是发布前本地门禁；它们最容易在 CI 之外悄悄腐化，改动相关路径时要主动跑。
- 双平台命令模板（`src/host/scripts.pwsh.ts` / `scripts.posix.ts`）必须同名导出，契约由 `src/types/scripts.ts` + `tests/types` 编译期断言锁死；行为差异（引号、编码、命令行长度、`$LASTEXITCODE`、循环体写法）是这类测试的高危区。

## 建模执行拓扑

除非当前配置证明相反，假设以下各层可以重叠：

1. 一个 Vitest 文件内的测试。
2. 不同的 Vitest 文件或 worker 进程。
3. 一个 job 内独立的 Vitest 或仓库门禁进程。
4. 共享同一宿主的不同 CI job。

进程隔离不隔离宿主端口、可预测的文件系统路径、外部服务、数据库、socket，也不隔离继承的子进程。对每个获取到的资源，说清它的拥有者、原子分配机制、可观察的就绪信号、注册的清理，以及静默完成信号。

不要因为一个 fixture 缺隔离就把整个套件串行。先缩小独占范围或改变资源分配方式。串行的 Vitest 块保护不了来自另一个文件、进程、job 或 runner 的宿主资源。

## 原子分配资源

用资源拥有者自己的分配器，而不是「先检查可用、稍后再占用」：

- 网络 fixture 用 `listen(0)` 绑定回环地址，只在服务器报告已监听后读取实际地址。绝不先扫描空闲端口再绑定。
- 用 `mkdtemp` 建私有的每测试临时根；不要占用可预测的共享路径。
- 共享数据库、socket、会话与输出位置给每测试唯一的命名空间。
- 路径必须不存在时用独占创建。
- 稳定的录制标识与临时传输地址分开。在 fixture 内部做转换，而不是强迫活的资源使用录制值。

只作为解析输入或期望值出现的字面路径与 URL 不是被占用的资源，不要因为它们看起来固定就去改写。

## 隔离进程全局状态

把 `process.env`、`cwd`、假时钟、locale 与时区、模块 mock、注册表、console hook、`globalThis` 和全局 `fetch` 拦截都当作独占可变资源。

优先使用注入的依赖或实例内的适配器。必须改动时：

- 记录原值是「不存在」还是「存在」；
- 精确恢复那个状态；
- 立即注册恢复；
- 用 `try/finally` 包住最小的改动范围；
- 失败发生在局部 `finally` 之前时留下 `afterEach` 兜底；
- 只拦截 fixture 拥有的那条确切请求或调用。

## 尊重平台语义

CI 在 Windows 与 POSIX 上跑同一套测试，操作系统拥有的值不一定按测试写入的样子读回来：

- 写回一个值，只在断言能容忍写回失败时才安全。恢复文件 `mtime` 用于证明指纹失效在任何平台都成立；用于证明记录仍然有效则假设了无损往返，而 NTFS 的 100 纳秒刻度给不出小数毫秒。断言依赖恢复结果时，从一次新的读取取期望值，而不是从记忆中的值。
- Windows 的环境变量名大小写不敏感：把 `http_proxy` 与 `HTTP_PROXY` 当两个键种进去，在那边只有一个条目。
- Windows 异步释放文件句柄：POSIX 上立刻完成的改名或删除，在那边需要按实测竞争量做有界重试。
- Windows 没有 POSIX 的权限与信号语义。依赖它们的用例显式平台跳过并写明理由，而不是把断言在所有平台上一并弱化。
- PowerShell 侧的特有陷阱（文本走 stdin 单进程、`.ps1` 测试文件必须带 BOM、命令行长度上限、native 非零退出不抛）已有台账条目，改动相关代码前按编号复查。

优先选择在所有平台都成立的观察。确实做不到时，在该平台显式排除。

## 按 lane 预算超时

`describe` 或单个用例的 timeout 是覆盖 runner 的 `--testTimeout`，而不是让位给它；低于该 lane 预算的值会压低 CI 已经给出的额度，而同一个字面量在默认值更小的宿主上又读作放宽。受进程创建约束的套件取 lane 预算；更紧的值要带上更紧的理由。

抬高 hook 预算要同时抬测试预算。安装与 teardown 付同样的竞争成本，只抬用例预算只是把受竞争影响的失败挪进 `afterEach`。

超时本身是被测对象时，让外层等待远大于被测超时。证明 20 ms 截止时间会触发的用例不能和 harness 自己的等待赛跑，否则负载决定谁先报告。

## 按状态同步

固定 sleep 不是安装完成或清理静默的证据。

- 等待显式的就绪事件、握手、状态转移、自己拥有的 promise，或外部可观察的条件。
- 用 deferred promise 或 barrier 把竞态放在确定的位置，并证明相关操作确实重叠。
- 超时只用来兜底等待，绝不用来让断言成立。
- 除非调度顺序本身就是被测的产品行为，不要断言依赖调度器的顺序。
- 时间本身是被测对象时，注入或伪造时钟，并且总是恢复真实定时器。

## 静默 teardown

获取后立即注册清理，使断言失败也能释放资源。清理要停止新的回调或请求、解绑监听、恢复全局钩子、终止自己拥有的工作，并 await 子进程退出、服务器关闭、worker 终止或等价的完成信号。

只调 `abort()`、`close()` 或 `kill()` 而不 await 自己拥有的完成信号是不完整的 teardown。存在延迟完成可能时，证明清理能阻止它改动另一个测试。

## 证明预期回归

- 可行时，先观察一个普通回归在修复前失败。
- 新的静态或语料守卫，先临时引入被拒绝的案例，观察它按预期失败。
- 竞态用 barrier 证明重叠；只重复执行不算竞态测试。
- 端口、socket、共享路径、子进程或其他宿主资源相关时，跨进程隔离是修复的一部分就用独立的测试进程并发跑。
- fixture 自带截止时间启动子进程时，先断言没有信号或超时结束了子进程，再断言其退出码，这样被杀的进程报告为超时而不是状态不匹配。
- 验证外部状态、事件、文件、日志、退出码或清理结果，而不是相信组件自己的报告。

压力运行是确定性回归的补充，不替代它。

## 拒绝 flake 掩盖式修复

不要把下列做法当作确定性本地测试的根因修复：

- 不指出所等状态就抬高超时；
- 加重试；
- 让所有文件串行；
- 吞掉错误或 unhandled rejection；
- 弱化断言；
- 把不稳定的行为规范化掉；
- 断言或清理前加 sleep。

唯一例外是受真实外部 provider 影响的瞬态测试（探针依赖本机 dsh 安装时属于这一类）；例外留在外部边界。

恢复预算不算掩盖。把套件抬回它本来就有的 lane 预算，或按 runner 上实测到的竞争量调整有界重试，两者都指明了所等的工作并归还了 lane 已给的额度；它们没有为未审视的等待发明余量。

## 诊断已有 flake

已有的概率性 CI 失败，读[CI flake 诊断](references/ci-flake-diagnosis.md)。纯诊断请求保持只读：报告原因与证据，除非用户同时要求修复。

## 验证与报告

对受影响的行为跑最小的聚焦回归。只在改动拥有该风险时补充拓扑特定的证据：

- 全局改动需要恢复证据；
- 生命周期或子进程工作需要静默 teardown 证据；
- 端口、socket 或共享路径需要独立进程并发证据；
- 新守卫需要负控制。

报告实际的命令与观察到的结果；不要把重试、跳过的测试或待跑的 CI 描述成通过。
